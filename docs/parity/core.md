# Core parity matrix

| SQLAlchemy feature | Status | Proving test | Notes |
| --- | --- | --- | --- |
| SQLite `text()` with positional and named bound parameters | partial | `tests/test_text.py`, `tests/test_sqlite_text.py`, `tests/test_executemany.py` | Public `text()` supports native SQLite `:name`, `@name`, and `$name` binds, escaped `\\:` literal colons, duplicate names, ignored extra keys, missing-key `StatementError`, buffered keys/rowcount, and executemany for named mappings and positional rows. Documented differences: `@name`/`$name` are a Catalyst extension (SQLAlchemy text() only parses `:name`); binds inside string literals are left literal by SQLite's own parameter parser where SQLAlchemy's regex would error or mangle; Catalyst's `StatementError` is a bare class without SQLAlchemy's `.orig`/`.params`/`.statement` attributes; `?NNN` numbered placeholders with a mapping raise `ProgrammingError` in both. `bindparams()` typing and outparams are unsupported; broader dialect and transaction parity remain open. |
| Core expression AST: metadata, `select` / `insert` / `update` / `delete`, SQLite SQL and binds | partial | `tests/test_expression.py` | SQLite compilation and ordered bound values cover select projections/table expansion, where chaining, boolean groups, relational/arithmetic operators, `IN`, `LIKE` (including escape), NULL/scalar `IS`, BETWEEN, ordering, limit/offset, literal DML values and where clauses (expression-valued DML `values()` is unsupported), minimal `count`/`lower`, and identifier quoting. SQLAlchemy 2.1.8 comparison checks SQL strings and bind values as dictionaries (order-insensitive). Arithmetic parenthesization follows SQLAlchemy's `is_precedent`/`_natural_self_precedent` rules (including `+`/`*`/`AND`/`OR` self-associativity and the SQLite `left / (right + 0.0)` true-division rewrite), unlabeled non-column select items receive `anon_N` labels with an independent counter, empty `select()` renders `SELECT`, empty `and_()`/`or_()` (with a `DeprecationWarning` instead of SQLAlchemy's `SADeprecationWarning`) flatten away including the whole `WHERE` clause, and `NOT` grouping covers arithmetic and nested negation. Known rendering differences: parameter dictionary insertion order can differ; bare Boolean literals render as SQLite `1`/`0` where SQLAlchemy renders `true`/`false`; string-operand `+` renders `+` where SQLAlchemy renders `||` for string-typed operands; the Rust parser rejects expression nesting at depth 2000 whereas SQLAlchemy accepts deeper trees. Type-aware binds/results for direct typed columns and expressions are covered separately in `tests/test_types.py`; arbitrary expression result type propagation remains incomplete. No joins, aliases, CTEs, window functions, distinct, group_by, having, or correlated subqueries. Multiple-table selection is unsupported. The compiler is SQLite-only; aliases and other dialect renderers remain later work. |
| SQLite DDL compilation and `create_all` / `drop_all` / `Table.create` / `Table.drop` | partial | `tests/test_ddl.py` | Rust renders `CREATE TABLE` (SQLAlchemy text layout including leading/trailing newlines) with INTEGER/VARCHAR(n)/TEXT/BOOLEAN/FLOAT/DATETIME types, single and composite `PRIMARY KEY`, `NOT NULL` (nullable defaults: False for primary keys, True otherwise; explicit `nullable=True` wins), column-level `UNIQUE`, and `server_default` string literals with `''` escaping; client-side `default=` is metadata-only like SQLAlchemy. `MetaData.create_all`/`drop_all` and `Table.create`/`drop` accept sync and async engine binds with SQLAlchemy `checkfirst` semantics implemented as `PRAGMA main.table_info` then `PRAGMA temp.table_info` probes on the checked-out connection (temp probes are included for semantic parity; Catalyst cannot create temp tables). DML round trips and row behavior are compared against SQLAlchemy on real memory engines. Out of scope and unimplemented: CHECK constraints, foreign keys, table-level constraints/unique constraints spanning columns, indexes, non-string `server_default` (TextClause/raw SQL), `CREATE TABLE ... SELECT`, schema-qualified names, and DDL event hooks. |
| Transactions and savepoints (SQLite) | partial | `tests/test_transaction.py` | Physical pool-slot transaction state implements commit-as-you-go autobegin, explicit root transactions, arbitrary nested savepoints, engine transaction context, rollback on close, and pool reset-on-return for checkouts dropped without `close()`. In-memory engines serialize all logical checkouts through one SQLite handle: transactions are shared across wrappers, sibling statements join an open transaction, and only a holder with its own transaction (explicit or autobegin) can commit, roll back, or roll back on close - exactly matching SQLAlchemy's SQLite `:memory:` default pool behavior; a fresh holder's commit/rollback/close are no-ops and leave a sibling's transaction intact. File-engine physical connections and transactions remain independent. Verified against SQLAlchemy for tested commit/rollback, savepoint, DDL, result, and invalid double-begin cases. Documented differences: `RootTransaction.commit()`/`rollback()` after the holder's transaction already ended raises matching `InvalidRequestError`; a savepoint handle used after its root ended raises clean `InvalidRequestError` where SQLAlchemy warns and no-ops; releasing an outer savepoint with an inner still active also raises `InvalidRequestError` where SQLAlchemy surfaces a driver error after a warning; context-manager exit on an already-ended transaction no-ops where SQLAlchemy warns. Raw text execution still uses leading-keyword DML classification, so CTE-prefixed DML (`WITH ...`) reports -1. Compiled expressions carry statement kind from Rust compilation and classify INSERT/UPDATE/DELETE explicitly. Two-phase transactions, transaction event hooks, isolation-level configuration, and non-SQLite dialects are unsupported. |
| SQLAlchemy-style exception names and supported DBAPI subclass hierarchy | partial | `tests/test_errors.py`, `tests/test_engine_options.py` | Supported exception classes are compared with SQLAlchemy; constructors, attributes, and the full exception set are not covered. `CatalystError` is an alias of `SQLAlchemyError`. `NoSuchModuleError` is added; absent drivers raise `ModuleNotFoundError` with a different message than SQLAlchemy's (class parity verified). |
| SQLite URL parsing and query configuration | partial | `tests/test_engine_options.py` | Matches tested memory, relative, absolute, and `sqlite+pysqlite://` driver-suffixed paths. URL grammar, escaping, credentials, fragments, and exact parser diagnostics are not comprehensive. URL query arguments are ignored with a `RuntimeWarning` like SQLAlchemy's pysqlite dialect; pool options must be passed as keyword arguments. |
| SQLite engine options (`pool_size`, `max_overflow`, `pool_timeout`, `timeout`, `echo`, `future`) | partial | `tests/test_engine_options.py` | Pool sizing, overflow, timed checkout, SQLite busy timeout, statement echo, `future=True`, invalid `future=False`, and unknown-option TypeError class are tested against SQLAlchemy. Other SQLAlchemy execution/event/pool options are unsupported. Documented differences: non-finite timeouts raise `ArgumentError` where SQLAlchemy accepts `inf`; negative `pool_size`/`pool_timeout` raise `ArgumentError` where SQLAlchemy accepts them; `echo`/`future` accept SQLAlchemy's string truthiness forms. |
| Dialect registry and unsupported driver errors | partial | `tests/test_engine_options.py` | Tiny Python registry recognizes SQLite and known PostgreSQL/MySQL dialect prefixes. Unknown dialect/plugin errors use `NoSuchModuleError`; known-but-uninstalled drivers raise `ModuleNotFoundError` matching SQLAlchemy's class (message text differs). No non-SQLite drivers are implemented. |
| SQLite Core/text executemany | partial | `tests/test_executemany.py` | Compiled Core DML takes a list of parameter mappings; text statements accept mapping batches and positional SQL accepts positional-row batches. Rust receives the full batch in one FFI call, runs each execute on the same checked-out SQLite connection/implicit transaction and sums changes. SQLAlchemy differential tests cover multi-row insert/update/delete rowcounts, compiled statement defaults merged with row mappings (row values override defaults), heterogeneous row-key validation, text batches, SELECT executemany's `ProgrammingError`, and a uniqueness failure: earlier rows remain pending in the open transaction and can be rolled back, matching SQLAlchemy. For compiled Core statements, an empty parameter sequence falls back to one execution using the statement's compiled values (including `DEFAULT VALUES` for `insert(table)`), matching SQLAlchemy; `tests/test_executemany.py` covers empty-sequence insert/update/delete/select behavior. Empty `text()` batches remain a batch with one empty mapping and therefore raise `StatementError` for a missing bind when the statement requires one. Batch result rows/RETURNING are not implemented: DML batch results have no rows, so `.all()` returns `[]` where SQLAlchemy raises `ResourceClosedError`. Per-row error attribution includes a parameter group number, but Catalyst currently numbers groups starting at 1 while SQLAlchemy's second group is reported as 1; fully SQLAlchemy-shaped `.orig/.params` and rowcount on all SQLite edge cases are also not implemented. Compiled positional-tuple batches are rejected with `ArgumentError` (SQLAlchemy also rejects tuple/list rows for compiled Core); generators are rejected with a clean `ArgumentError` but are not accepted as SQLAlchemy does. Empty text parameter sequences resolve to an empty mapping and report missing named binds as `StatementError`. |
| Synchronous `create_engine` / `Engine.connect` / `Connection.execute` for SQLite text statements | partial | `tests/test_sqlite_text.py`, `tests/test_transaction.py`, `tests/test_engine_options.py`, `tests/test_types.py`, `tests/test_executemany.py` | Catalyst's engine, pooled file connections, singleton `:memory:` connection semantics (serialized checkouts with shared transaction boundaries), buffered `CursorResult`, context managers, dispose lifecycle, pool options and timed exhaustion, SQLite transaction lifecycle, typed Core processing, and tested executemany behavior are compared with SQLAlchemy. URL/options/dialect coverage is in `tests/test_engine_options.py`; gaps include partial SQLAlchemy URL grammar/error-message parity, memory pool semantics, and full SQLAlchemy import-error wrapping. |
