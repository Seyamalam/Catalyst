# Core parity matrix

| SQLite `text()` with positional and named bound parameters | partial | `tests/test_text.py`, `tests/test_sqlite_text.py`, `tests/test_executemany.py` | Public `text()` supports native SQLite `:name`, `@name`, and `$name` binds, escaped `\\:` literal colons, duplicate names, ignored extra keys, missing-key `StatementError`, buffered keys/rowcount, and executemany for named mappings and positional rows. | Core expression AST: metadata, `select` / `insert` / `update` / `delete`, SQLite SQL and binds | partial | `tests/test_expression.py` | SQLite compilation and ordered bound values cover select projections/table expansion, where chaining, boolean groups, relational/arithmetic operators, `IN`, `LIKE` (including escape), NULL/scalar `IS`, BETWEEN, ordering, limit/offset, literal DML values and where clauses (expression-valued DML `values()` is unsupported), minimal `count`/`lower`, and identifier quoting. | Transactions and savepoints (SQLite) | partial | `tests/test_transaction.py` | Physical pool-slot transaction state implements commit-as-you-go autobegin, explicit root transactions, arbitrary nested savepoints, engine transaction context, rollback on close, and pool reset-on-return for checkouts dropped without `close()`. In-memory engines serialize all logical checkouts through one SQLite handle: transactions are shared across wrappers, sibling statements join an open transaction, and only a holder with its own transaction (explicit or autobegin) can commit, roll back, or roll back on close - exactly matching SQLAlchemy's SQLite `:memory:` default pool behavior; a fresh holder's commit/rollback/close are no-ops and leave a sibling's transaction intact. File-engine physical connections and transactions remain independent. Verified against SQLAlchemy for tested commit/rollback, savepoint, DDL, result, and invalid double-begin cases. Documented differences: `RootTransaction.commit()`/`rollback()` after the holder's transaction already ended raises matching `InvalidRequestError`; a savepoint handle used after its root ended raises clean `InvalidRequestError` where SQLAlchemy warns and no-ops; releasing an outer savepoint with an inner still active also raises `InvalidRequestError` where SQLAlchemy surfaces a driver error after a warning; context-manager exit on an already-ended transaction no-ops where SQLAlchemy warns. Raw text execution still uses leading-keyword DML classification, so CTE-prefixed DML (`WITH ...`) reports -1. Two-phase transactions, transaction event hooks, and isolation-level configuration are unsupported; the async savepoint surface also covers PostgreSQL and MySQL (see the async matrix). |

| SQLite Core/text executemany | partial | `tests/test_executemany.py` | Compiled Core DML takes a list of parameter mappings; text statements accept mapping batches (a positional-row batch on `text()` is a Catalyst extension; SQLAlchemy requires a list of mappings), and positional SQL accepts positional-row batches. Rust receives the full batch in one FFI call, runs each execute on the same checked-out SQLite connection/implicit transaction and sums changes. SQLAlchemy differential tests cover multi-row insert/update/delete rowcounts, compiled statement defaults merged with row mappings (row values override defaults), heterogeneous row-key validation, text batches, SELECT executemany's `ProgrammingError`, and a uniqueness failure: earlier rows remain pending in the open transaction and can be rolled back, matching SQLAlchemy. ## Known gaps and documented differences

Verified against code and the proving suites; each item is either an explicit `not started`/`partial` row above or a behavioral difference the tests document rather than reproduce:

- **Executemany parameter-group numbering**: Catalyst reports groups 0-based; SQLAlchemy reports the second group as 1 (`tests/test_executemany.py`).
- **DML results carry no rows**: `.all()` on an INSERT/UPDATE/DELETE result returns `[]` where SQLAlchemy raises `ResourceClosedError`; RETURNING is unimplemented.
- **SQLite `:memory:` pool semantics**: all logical checkouts serialize through one shared SQLite handle with shared transaction boundaries — matching SQLAlchemy's pysqlite `:memory:` default pool, a deliberate reproduction, not a gap.
- **SQLite RELEASE-commits gotcha not reproduced**: pysqlite implicitly BEGINs only before DML, so SQLAlchemy's first-savepoint `RELEASE` commits the transaction; Catalyst issues an explicit `BEGIN`, so `ROLLBACK` still undoes released-savepoint work (`docs/m4-tail-ground-truth.md`, `tests/test_savepoints.py::test_savepoint_first_operation_release_commits_sqlite_gotcha`).
- **Recursion depth**: the Rust expression parser rejects nesting at depth ~2000 with a catchable `RecursionError`; SQLAlchemy accepts deeper trees (`tests/test_expression.py::test_deep_public_expression_raises_recursion_error`).
- **Bare Boolean literals** render as SQLite `1`/`0` where SQLAlchemy renders `true`/`false`.
- **`text()` extensions**: `@name`/`$name` binds are a Catalyst extension (SQLAlchemy `text()` parses only `:name`); binds inside string literals follow SQLite's own parser where SQLAlchemy's regex would error.
- **Positional-row batches on `text()`** are a Catalyst extension; SQLAlchemy requires a list of mappings for text statements.
- **Engine options**: non-finite timeouts and negative `pool_size`/`pool_timeout` raise `ArgumentError` where SQLAlchemy accepts them; URL query arguments are ignored with `RuntimeWarning` like SQLAlchemy's pysqlite dialect.
- **Sync engines are SQLite-only**: `create_engine` has no PostgreSQL/MySQL sync driver (async drivers only — see `docs/parity/dialects.md`).
- **Pool features absent**: no `pool_pre_ping`, recycle, per-connection options, or `NullPool`/`StaticPool`/`QueuePool` class selection.
