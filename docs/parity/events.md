# Events parity matrix

| SQLAlchemy feature | Status | Proving test | Notes |
| --- | --- | --- | --- |
| Session events (`SessionEvents` / `event.listen`) | done | `tests/test_session_events.py` | `catalyst.event` implements `listen`/`contains`/`remove`/`listens_for` on the `Session` class, `Session` subclasses, session instances, and the `SessionEvents` interface target (registers against `Session` like SQLAlchemy); unknown names raise `InvalidRequestError` ("No such event ... for target ..."). Class-level listeners live in a weak-keyed per-class registry dispatched base-first along the MRO (matching SA's registration-time propagation), then instance listeners. The full SA 2.1.8 firing matrix is dispatched Python-side at UOW seams (the Rust `NativeUow` stays pure bookkeeping): add → `after_transaction_create, before_attach, after_attach, transient_to_pending`; flush → `before_flush, after_transaction_create, after_begin, after_flush, <state events>, after_flush_postexec, after_transaction_end` wrapped in a flush "subtransaction" marker; commit adds `before_commit`/`after_commit` with `deleted_to_detached` after `after_commit`; rollback → `after_rollback, <transition events>, after_transaction_end, after_soft_rollback`; `loaded_as_persistent` fires only for newly-registered identity-map instances (hydration, `get`, `merge` of detached); `expunge`/`expunge_all`/`close` fire per-status detach events. `before_flush(session, flush_context, instances)` sees live `session.new`/`dirty`/`deleted` and `session.add` inside it joins the same flush. `after_bulk_update`/`after_bulk_delete`/`do_orm_execute` are accepted but never dispatched (Catalyst has no legacy `Query` API; 2.0-style ORM DML does not fire them in SA either — documented). `Session.close()` fires detach events plus `after_transaction_end` when a transaction was active; a clean close emits nothing (suite defect fixed: earlier draft asserted close always silent). |
