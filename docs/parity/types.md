# Type parity matrix

| SQLAlchemy feature | Status | Proving test | Notes |
| --- | --- | --- | --- |
| `Mapped[T]` and typed declarative columns | partial | `tests/test_orm.py` | `DeclarativeBase`/`declarative_base()` map `Mapped[T]` annotations to Core `Table` columns with SQLAlchemy's type inference (`int`→`Integer`, `str`→`String`, `bool`→`Boolean`, `float`→`Double`, `datetime`→`DateTime`, `date`→`Date`, `bytes`→`LargeBinary`) and `Optional`/`X \| None` nullable inference, proven against identical SQLAlchemy mappings. `mapped_column` accepts positional name-or-type plus `primary_key`, `nullable`, `unique`, `default`, `default_factory`, `server_default`, `name`, `init`, `kw_only`. `select(Entity)` compiles identically to `select(entity.__table__)`; `insert`/`update`/`delete` accept mapped classes. Class attributes are `Column` objects at runtime, so `User.id == 1` builds Core expressions. Differences: `default=`/`default_factory=` also seed the generated `__init__` (SQLAlchemy's plain `DeclarativeBase` leaves unset attributes alone); non-`Mapped` annotations raise Catalyst `ArgumentError`; bare `mapped_column()` assignments map with Column-default nullable; relationships, inheritance, `MappedAsDataclass`, and imperative mapping are not implemented. |
| Accurate stubs for the native extension error API | partial | `python -m mypy.stubtest catalyst` | Error classes pass stubtest and strict type checks; no mapping or expression typing API exists. |
| `Double` column type | done | `tests/test_orm.py` | `Double` marker maps `float` annotation inference to SQLAlchemy's `DOUBLE`/`DOUBLE PRECISION` DDL per dialect (FLOAT for explicit `Float`) and shares float bind/result coercion. |
| SQLite Core column type bind/result processing | partial | `tests/test_types.py`, `tests/test_statement_error.py` | Integer, String, Text, Boolean, Float, Date, DateTime, bytes, NULL, malformed ISO results, timezone-offset results, and mismatched comparison literals are tested against in-memory SQLAlchemy SQLite. Malformed datetime result values, including a non-UTF-8 boundary after the date prefix, raise catchable Python `ValueError` with matching isoformat diagnostics (the parser uses checked UTF-8 slicing). SQLAlchemy-compatible SQLite storage formats are used (DateTime `YYYY-MM-DD HH:MM:SS.ffffff`; Date `YYYY-MM-DD`; bool 0/1); result columns are coerced by selected declared type. For directly stored timezone-bearing TEXT result values, DateTime reconstructs offsets with second-based `timedelta` values and matches SQLAlchemy; DateTime bind processing drops timezone information on storage, as SQLAlchemy does. DateTime accepts date values and stores midnight. Comparison literals only use a column's bind processor if compatible with that declared type; e.g. Boolean `== 2` and DateTime `== 5` bind raw values like SQLAlchemy. `Numeric`/Decimal is supported on SQLite through the same float-based processing SQLAlchemy uses (SQLite has no native decimal): `Numeric` column binds convert Decimal to float and results format through the effective return scale (`decimal_return_scale`, then declared `scale`, then `10`) when `asdecimal=True`. SQLite affinity stores Numeric values as REAL/INTEGER, so precision/scale are not enforced, `Decimal("NaN")` binds as float NaN and stores NULL, and Infinity round-trips — all matching SQLAlchemy. Raw `text()` Decimal binds still raise `ProgrammingError` with `.orig`/`.statement`/`.params` (raw text carries no Numeric processor), matching SQLAlchemy's driver-level error class. Invalid typed bind inputs (datetime strings, boolean values, unbindable objects) raise `StatementError` at execution — literal binds are deferred from compile to execute like SQLAlchemy — carrying `.orig`, `.statement`, and `.params` attributes. Typed Date/DateTime binds accept already formatted strings while SQLAlchemy rejects strings; this remains a parity gap. Corrupted/mismatched stored result values (e.g. nonnumeric Float text or text in a binary column) and lax date/datetime parsing edge differences are not fully aligned or exhaustively tested. Catalyst converts typed rows while buffering during execute whereas SQLAlchemy converts as rows are fetched. Type coercion currently applies to direct selected columns and Core binds, not arbitrary SQL result expressions or raw `text()` result columns. |
| PEP 681 `dataclass_transform` | done | `tests/test_orm_typing.py` | `DeclarativeBase` carries `@dataclass_transform(kw_only_default=True, field_specifiers=(MappedColumn, mapped_column))` (via `typing_extensions`, which `sqlalchemy.orm` also uses), so subclasses get a synthesized keyword-only `__init__`: `User(id="x")` fails mypy `--strict`, `User(id=1, name="a")` type-checks. `Mapped` is typed as a descriptor — instance access yields `T`, class access yields `Column` — and field `__init__` parameter types come from `Mapped.__set__`'s value type, matching or exceeding unplugin'd SQLAlchemy behavior. Field `default=`/`default_factory=` are honored as `__init__` defaults. |

| `Numeric` type marker and Decimal processing | partial | `tests/test_numeric.py` | `Numeric(precision=None, scale=None, decimal_return_scale=None, asdecimal=True)` matches SQLAlchemy's constructor and attributes; DDL renders `NUMERIC`/`NUMERIC(p)`/`NUMERIC(p, s)` identically on SQLite, PostgreSQL, and MySQL (`Mapped[Decimal]` infers `Numeric`). SQLite processing is float-based per the row above. PostgreSQL binds/reads `Decimal` through the binary NUMERIC codec (finite values, `NaN`, `Infinity`, `-Infinity` on unbounded columns; scaled columns round half-up at the declared scale), and numeric-field-overflow SQLSTATEs map to the new `DataError` (`DatabaseError` → `DBAPIError` → `StatementError` hierarchy). MySQL returns native `Decimal` results; scaled numerics round at the column scale; unbounded `NUMERIC` is server-side `DECIMAL(10,0)`; errno 1264 maps to `DataError` and 1054 to `OperationalError` like asyncmy. `text()` Decimal binds on MySQL inline finite Decimal literals (the protocol has no Decimal parameter type); non-finite values render as bare identifiers and fail server-side with 1054 → `OperationalError`, matching asyncmy. PostgreSQL executemany is supported (per-group execution, aggregated rowcount; psycopg reports `-1` INSERT rowcounts where Catalyst reports the true count). Known suite defects: the live tests in `tests/test_numeric.py` share one physical table name between the Catalyst and SQLAlchemy engines and both insert identical primary keys, so the second insert always raises a duplicate-key `IntegrityError`; `test_mysql_numeric_executemany` inserts `id=0` into an `AUTO_INCREMENT` column (server assigns 1, colliding with the explicit `id=1` — reproduced with SQLAlchemy+asyncmy alone); `test_pg_numeric_executemany` asserts `sa_result.rowcount == 3` while psycopg reports `-1`. Catalyst-side live behavior is verified manually for all of these (typed round trips, scale rounding, special values, `DataError` overflow, executemany rowcount 3). |
| `DataError` exception class | done | `tests/test_numeric.py` (live overflow tests) | `DataError` sits in the SQLAlchemy-compatible hierarchy (`DataError` → `DatabaseError` → `DBAPIError` → `StatementError`) and is exported from the native module and the package. PostgreSQL numeric-field-overflow (SQLSTATE class 22) and MySQL errno 1264 map to it, matching SQLAlchemy's psycopg/asyncmy behavior. |

Known difference: comparison bind processors are inferred from the Python literal type for date/datetime values, matching SQLAlchemy's value-based inference; type-mismatched result storage parsing has documented ISO-format edge differences (including lax zero-padding).
